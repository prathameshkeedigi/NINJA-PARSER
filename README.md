# Build_ninja_proof: our build.ninja parser reads build.ninja exactly like Ninja

Team 10, Dependency Aware Parallel Build System.

## The question this folder answers
Our engine reads `build.ninja` (written by CMake) and turns it into a graph of tasks (a DAG).

**Can a parser of our own read build.ninja correctly, including every node, every arrow and every command?**

To answer it, we ran our parser on 20 real CMake projects and compared every answer with the answer of **Ninja itself**, the program that reads these files professionally.

## Result
**20 of 20 projects pass all four checks.**

| What was compared | Total over the 20 projects |
|---|---|
| File nodes, each compared with `ninja -t query` | 2,521 |
| Expanded command lines, each compared with `ninja -t commands` | 507 |
| Tasks executed using only our parser's output | 143 |
| Programs whose printed output matched the Ninja-built program | 20 of 20 |

The full table is in [results/SUMMARY.md](results/SUMMARY.md).

## The four checks (done for every project)
CMake configures each project twice, into two separate, fresh folders: `builds/<project>/by_ninja` and `builds/<project>/by_our_parser`.

| Check | Question | How |
|---|---|---|
| **1. Graph** | Does our parser see the same files and the same arrows? | For **every** file node, our parser prints the same text that `ninja -t query <node>` prints: the rule that produces it, its inputs (with `\|` implicit and `\|\|` order-only markers), and the steps that use it. Both texts must be identical, character for character. |
| **2. Commands** | Does our parser produce the same command lines? | For **every** build step, our fully expanded command must be identical to `ninja -t commands`, in text and in order. |
| **3. Order** | Is our task order valid? | Every task in our Kahn (topological) order must come after every task it waits for. |
| **4. Real build** | Does the result actually work? | `by_ninja` is built with real Ninja. `by_our_parser` is built **without Ninja**, by running only the commands our parser produced, one at a time, in our order. Then the programs from both folders are run, and what they print must be identical. |

## The 20 projects
Each small project has 3–4 C files and tests one feature of build.ninja. Project 20 is the real zlib library.

| # | Project | build.ninja feature it tests |
|---|---|---|
| 01 | basic_exe | simplest compile + link graph |
| 02 | static_lib | static library built with `ar` |
| 03 | shared_lib | DLL: the link step has two outputs (`.dll` and import library `.dll.a`) |
| 04 | lib_chain | app → libmid → libbase |
| 05 | generated_header | a program built during the build writes `keywordhash.h` (like SQLite's mkkeywordhash) |
| 06 | generated_source | one step writes `parse.c` and `parse.h` (like lemon); `parse.c` is then compiled |
| 07 | compile_definitions | a define containing a space and quotes: `-DGREETING="\"hello world\""` |
| 08 | include_dirs | several `-I` folders |
| 09 | subdirectories | `add_subdirectory`, nested CMakeLists |
| 10 | object_library | the same `.obj` files linked into two programs |
| 11 | custom_target_postbuild | a custom target that always runs, and a POST_BUILD copy step |
| 12 | configure_file | `config.h` generated by CMake at configure time |
| 13 | multiple_executables | one library used by three programs |
| 14 | interface_lib | INTERFACE library (adds only a define and an include folder) |
| 15 | response_files | `rspfile` / `rspfile_content` (inputs passed through an `@file`) |
| 16 | spaces_in_paths | folder and file names with spaces (`$ ` escape) |
| 17 | ctest | `enable_testing`, `add_test` |
| 18 | install_rules | `install()`: adds install steps; the install path contains spaces |
| 19 | precompiled_header | a separate step compiles `common.h` into a `.gch` file |
| 20 | zlib | zlib 1.3.1, unmodified: 17 distinct C files compiled in 34 compile steps (each library C file is compiled once for the DLL and once for the static library), 4 test programs, windres resource step |

**zlib source:** downloaded from https://github.com/madler/zlib/releases/download/v1.3.1/zlib-1.3.1.tar.gz, SHA-256 `9a93b2b7dfdac77ceba5a558a580e74667dd6fede4585b91eefb60f03b72df23`.

During configure, zlib's own CMakeLists.txt renames `zconf.h` to `zconf.h.included` in its source folder. This is zlib's normal behaviour for out-of-source builds. We did not edit any zlib file.

## Can these checks fail? (negative control)
A check that always says PASS proves nothing. So we made 5 copies of our parser, each with one deliberate bug, and ran the same checks with each copy. **All 5 bugs were caught.** See [results/NEGATIVE_CONTROL.md](results/NEGATIVE_CONTROL.md).

Example: bug B5 lets a task wait only for its explicit inputs. On project 05 the broken parser compiled `tokenize.c` **before** `keywordhash.h` had been generated, and gcc failed with `keywordhash.h: No such file or directory`. Check 4 caught it.

The table also shows that each feature needs a project that uses it. For example, the escaped-space bug B2 is caught only by project 16, the only project with spaces in its paths. This is why the projects cover different features.

## Evidence files
For each project, `results/<project>/` holds the raw files. Any two of them can be compared in cmd with `fc`.

| File | Contents |
|---|---|
| `check1_ninja_query.txt` / `check1_parser_query.txt` | Ninja's and our parser's description of every node |
| `check2_ninja_commands.txt` / `check2_parser_commands.txt` | every expanded command, from Ninja and from our parser |
| `check3_parser_order.txt` | our task order and what each task waits for |
| `check4_build_log_ninja.txt` / `check4_build_log_our_parser.txt` | the two builds |
| `check4_program_output_ninja.txt` / `check4_program_output_our_parser.txt` | what the programs printed |
| `result.json` | the numbers for the summary table |

Example: `fc results\20_zlib\check2_ninja_commands.txt results\20_zlib\check2_parser_commands.txt` prints `FC: no differences encountered`.

To run the proof yourself, see [How to run the proof yourself](#how-to-run-the-proof-yourself) at the end of this file.

```
  tools/      ninja_parse.py (our parser, 410 lines), run_proof.py (the 4 checks), negative_control.py

```

## What this does NOT prove (limits)
- Every build.ninja tested here was written by **CMake 4.4.4 for C with gcc on Windows**. Files from other generators (Meson, GN) or other languages were not tested.
- The parser does not support Ninja's `|@` (validations) or `dyndep`. Neither appeared in any of the 20 files. If one does, the parser stops with an error instead of guessing.
- Check 3 checks our order against **our own** arrows, so it cannot catch a wrong arrow by itself. Wrong arrows are caught by check 1 (the inputs must match Ninja) and check 4 (the build must succeed), as bug B5 shows.
- Check 4 runs the tasks **one at a time**. Running them in parallel is the job of our execution engine (E3) and is not tested here.
- Header files that are **not generated** (like `mathops.h`) do not appear in build.ninja. The compiler reports them in `.d` files after compiling, and they are needed only for rebuild decisions (E2), not for the order. This is by design and is outside this proof.

## How to run the proof yourself
These steps are for **Windows**, typed in **cmd**. In total they take about 10 minutes.

### Step 1: Check what is already installed
```cmd
python --version
git --version
cmake --version
ninja --version
gcc --version
```
Every line must print a version number. If one prints `is not recognized as an internal or external command`, install that tool in Step 2.

### Step 2: Install what is missing
- **Python 3:** install from https://www.python.org/downloads/ and tick "Add python.exe to PATH" during setup.
- **Git:** install from https://git-scm.com/download/win
- **CMake and Ninja:**
  ```cmd
  python -m pip install cmake ninja
  ```
  If `cmake --version` still says "not recognized" afterwards, pip printed a warning naming the folder it used, for example `C:\Users\<you>\AppData\Roaming\Python\Python313\Scripts`. Add that folder to PATH (Step 2b).
- **gcc (MSYS2):** install MSYS2 from https://www.msys2.org/. Then, in the **MSYS2 UCRT64** terminal (not cmd), run:
  ```
  pacman -S mingw-w64-ucrt-x86_64-gcc
  ```
  gcc is then in `C:\msys64\ucrt64\bin`. Add that folder to PATH (Step 2b).

### Step 2b: Add a folder to PATH (only if Step 2 told you to)
Replace the folder in quotes with yours:
```cmd
powershell -NoProfile -Command "$p=[Environment]::GetEnvironmentVariable('Path','User'); [Environment]::SetEnvironmentVariable('Path', $p + ';C:\msys64\ucrt64\bin', 'User')"
```
Then **close cmd and open a new one** (Win+R → `cmd` → Enter), and repeat Step 1. A cmd window that was already open keeps the old PATH.

### Step 3: Download this repository
```cmd
cd /d %USERPROFILE%\Desktop
git clone https://github.com/prathameshkeedigi/NINJA-PARSER.git
cd NINJA-PARSER
```

### Step 4: Run the four checks on all 20 projects
```cmd
python tools\run_proof.py
```
This takes about 3 minutes. It prints one line per project. All 20 lines should look like this:
```
01_basic_exe                   q=PASS cmd=PASS order=PASS build+run=PASS  (8.0s)
```
The last line should be:
```
20 of 20 pass all checks; see results\SUMMARY.md
```
The script makes fresh build folders in `builds\` and rewrites `results\` with **your** computer's outputs. The `results\` stored in the repository are the outputs from the original run, kept for reference.

To check only some projects, give their names:
```cmd
python tools\run_proof.py 05_generated_header 20_zlib
```

### Step 5: Look at the evidence yourself
Open `results\SUMMARY.md` for the table. Then compare Ninja's answers with the parser's answers directly, using Windows' own file-compare command:
```cmd
fc results\20_zlib\check1_ninja_query.txt results\20_zlib\check1_parser_query.txt
fc results\20_zlib\check2_ninja_commands.txt results\20_zlib\check2_parser_commands.txt
fc results\20_zlib\check4_program_output_ninja.txt results\20_zlib\check4_program_output_our_parser.txt
```
Each should print `FC: no differences encountered`. Replace `20_zlib` with any other project name to check that project.

### Step 6 (optional): Run the negative control
```cmd
python tools\negative_control.py
```
This takes about 3 minutes. It runs the checks with 5 deliberately broken copies of the parser, in temporary folders only, and writes `results\NEGATIVE_CONTROL.md`. The last line should be:
```
5 of 5 bugs caught; see results\NEGATIVE_CONTROL.md
```

### If something goes wrong
| What you see | Cause | Fix |
|---|---|---|
| `cmake configure failed` in the line for a project | CMake could not find gcc | Check that `gcc --version` works in the same cmd window (Step 2b) |
| `'python' is not recognized` | Python is not on PATH | Reinstall Python with "Add python.exe to PATH" ticked |
| A check shows `FAIL` | the parser and Ninja disagree on your machine | Open that project's files in `results\<project>\` and compare them with `fc` to see the first difference |
